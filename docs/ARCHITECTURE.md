# Architecture

ahem is a Tauri 2 app: a Rust backend (`src-tauri/`) and a React + TypeScript interface (`src/`) in three webview windows — the main window, the dictation indicator and the quick panel at the tray icon. The interface calls Rust commands (`invoke`) and listens to typed events (`core-event`, `settings-changed`, `hotkeys-changed`); it only displays state and never parses message text. All OS-specific code lives in `src-tauri/src/platform/`. Dependencies and their licenses are in `DEPENDENCIES.md`.

## Frontend

Each page is a Vite entry: `index.html` → `main.tsx` (the main window), `indicator.html` → `indicator.tsx`, `tray.html` → `tray.tsx`.

- `main.tsx` — first lifts a pause of the hotkeys (`set_hotkey_suspended(false)`: a page reloaded while a hotkey was being recorded would leave none registered), then loads OS locales, settings, the last transcription and status, picks the interface language and renders the app.
- `App.tsx` — the full window:
  - The title bar: on Windows and Linux its own (`components/TitleBar.tsx`: a strip that drags the window and maximizes it on a double click, minimize / maximize / close in the app's style; `decorations: false` in `tauri.conf.json`, capability `window-controls`); on macOS the page runs under a transparent system bar (`titleBarStyle: Overlay`, hidden title) with the system window buttons in the top left corner above the brand, and the strip only drags.
  - Navigation in two labelled groups — Work: Dictation, Transcripts, History; Setup: Modes, Dictionary, Services, Models with the download percent of speech models — then the model state and Settings. The pages stay mounted. `targetPage` maps a link (a page, `settings:<tab>` or `mode:<id>`) to its page.
  - The message bar: save errors, settings that cannot be saved, taken hotkeys, missing engine.
  - Listens to `core-event`, keeps the settings and saves them one after another through `save_settings` (`Update` takes a change or a function of the settings saved last, so quick edits do not overwrite each other). The status (`get_status`: the hotkeys not registered, the engine) is read again on `settings-changed` (sent by every save) and `hotkeys-changed`; only the answer to the latest read counts.
- The look: design tokens and rules are in `App.css`, light and dark under `data-theme` / the OS scheme. On Windows and Linux the backend zooms the main window, the quick panel and the indicator 1.2 times; on macOS the zoom is 1.0 and the main window is 1.2 times smaller instead (`platform::UI_ZOOM`, `tauri.macos.conf.json`).
- `ui.tsx` — building blocks: icons, card and row, toggle, segments, radio, key caps, choice row, step tile, icon circle, select (its own floating list in the app's style, keys as in a system list: `stepOption`, `typedOption`), tabs, message bar, engine status, wave strip, progress; `useRoving`, a group of radios or tabs as the roles promise (Tab stops once in it, at the chosen item; the arrows, Home and End move the focus and choose, or with `manual` only move it and Enter or Space chooses — the list of modes while a new mode is a draft); `Modal`, a dialog drawn through a portal at the end of the page (Escape or a click beside it closes it, Tab goes round inside it, and the focus goes back where it was once it closes); `useConfirm` and `useConfirmKey`, destructive buttons that ask again (the second press within 3 s acts; a press sooner than `DELETE_GUARD_MS`, 400 ms, after the first is the second click of a double click and leaves the button armed); `pressGuard` (`usePressGuard`), which lets presses go for a while: a delete button for `DELETE_GUARD_MS` after it deleted, so the row that moved up under the pointer is not deleted too, and "Cancel" of the ChatGPT sign-in just after it appeared; `readOnFocus`, which reads what may change while the window is away (the microphones, the recent programs, the statistics after midnight) now and whenever the window gets the focus back; `useWindowSeen` (`watchSeen`, tested), whether the web view says the window is seen (WebKit says it is not when the window is hidden in the tray or minimized); `shownTitle` (the title of the screen shown, never one of a hidden screen) and `rowAfterRemoval` (the row in the place of a deleted one), where the focus goes after a screen changes or a row is deleted; `useFocusAfter` (`followFocus`, tested): before an action from the keyboard it notes the focused element and where to go if that element goes away with the action (a deleted row, a button that gives way to another; with `disabledIsGone`, one that stays disabled, and a target found disabled is looked for again at every drawing), and puts the focus there once it fell to the page — so a download's or a transcription's "Cancel" that goes when the work ends hands the focus to the row's first button or the entry's title, and a running file's "Open" or a meeting's "Start recording" and "Stop and transcribe", gone as the work ends or as the recording starts or stops in the quick panel, to the button in their place (followed from the moment they have the focus); `isComposing`, so the Enter or Escape that ends an input method's composition does not save, send or close a field; `useFocusAfterBusy`, which puts the focus back in a field once a check that disabled it was refused; `useCopied` and `afterCopy`: "Copied" for 2 s after a copy or, until the next copy, that the clipboard refused it (`last.copy_failed`).
- `present.ts` — texts of the state, and `latestOnly`, `commandFailure` and `ownMessages`, which bring the answers of commands to the window; `useStatus` (the backend's status — hotkeys registered, engine there — read again at `STATUS_EVENTS`, the settings and hotkeys changing, only the latest answer, for the main window and the quick panel); `microphoneOptions` (the choices of microphone, with "microphone disconnected" for a chosen one that is gone, in the settings and the quick panel); `newCapsuleVisit` (when the capsule grows in again: leaving rest, or a notice the backend shows by itself while at rest — `blocked`, `selection_failed`); `hero` (the dictation card: recording with a clock, recognition, processing, insertion, a calm outcome for 1.8 s, a failure until the next dictation, unavailable without a model or engine — a `blocked` notice whose reason has passed (a usable engine chosen since: `canRecognize`, or the engine there) and an engine failure once the engine loads again or another model is chosen (`forgetEngineFailure`) no longer show; its `warnings`, while that dictation runs and beside its own outcome, never beside another dictation's outcome nor while another dictation records, even once its own outcome came: the microphone went away midway, the text did not go to the history; `copyFailure` beside the copy button), `capsule` and `capsuleWarning` (the indicator's look and text; the warning of the dictation whose outcome is the notice takes the place of its success), `engineStatus`, `modeName`, `modeCaption`, `noticeText`, `saveErrorText`, `quote` (cut by characters as a reader sees them, `graphemes`: never inside a flag, an emoji sequence or a letter with its combining mark).
- `events.ts` — TypeScript mirror of `CoreEvent`; `useEvent` subscribes a component to a backend event (`core-event`; `settings-changed` and `hotkeys-changed`, named in `settings.ts`).
- `dictation.ts` — `reduce` (events → `View`, what the screen shows: the sessions, from which `phase` tells the phase, engine state, latest notice and `noticeSession`, the dictation whose outcome it is, the microphone lost during a recording (`microphoneLost`, until a dictation begins after that one's outcome: a dictation begun while it is still recognized does not take the warning from its outcome) and a text that did not go to the history (`historyFailed`, until the next dictation begins), last transcription, whether it can be recognized again, downloads, the file job). The input level stays outside `View`: `useLevel` keeps it in a ref that `levelAfter` updates, so twenty level events a second redraw nothing, and a level strip (`useLevelStrip` in `ui.tsx`) reads it at its own pace. Also `useRetry` ("Recognize again"), `hotkeyFromKey` (`KeyboardEvent.code` → backend syntax), `formatHotkey` and `hotkeyKeys` (keys by the sign on them as on a US keyboard: `` ` ``, `-`, `↑`, `Num 1`; on a Mac, Backspace, Enter, the forward Delete and Escape by a Mac keyboard's names: Delete, Return, ⌦, Esc).
- `settings.ts` — the `Settings` and `SaveError` types (mirror Rust), `Update`, load/save calls, `resolveLanguage`, mode helpers such as `choosableModes` and `withEnglish`.
- `services.ts` — the named services (OpenAI, Anthropic, Groq, Deepgram, DeepSeek; DeepSeek and Groq at their OpenAI-style addresses) with what each does (speech, text), `serviceOf` / `groupConnections` (connections by service, the ChatGPT account apart, the rest as own servers), `isChatGptAccount`, `hasLanguageModels` (Deepgram has none), `hostOf`, `monogram` (whole characters, an emoji too), `defaultModel` for a new mode.
- `logos.ts` — the services' marks on the Services page, drawn in the text color (sources in `DEPENDENCIES.md`). `assets/chatgpt-logo-white.svg` — OpenAI's mark for the "Continue with ChatGPT" button.
- `shortcuts.ts` — every hotkey of the app in one list (`Shortcut`: the main one, by application, a mode's own, a mode's selected text); `modeLaunch` tells how a mode is started.
- `appRules.ts` — modes by application on the interface side: a mode's rules (`appRulesView`: the main mode shows its rules too, removable, with a note that there the "by application" hotkey keeps it once another mode is main; its last rule removed, the focus goes to the list of modes, `focusAfterRule`), adding (one rule per program; a rule of another mode for the same program moves) and removing one, the recent programs to offer (`offeredApps`) and typed names (`typedApp`).
- `languages.ts` — the spoken languages of the engine (`list_languages`), named in the interface language through the browser's `Intl` data.
- `replacements.ts` — `phraseKey` (an entry's variants as the backend compares them) and `mergeReplacements` (an added or imported entry takes the place of one with the same phrase); a row's change or delete finds its entry by what it holds, also by what it sent and has not seen saved yet (`rowEntries`, `sentAfter`), so a delete pressed right after a change finds the row.
- `onboarding.ts`, `stats.ts`, `meetings.ts`, `quick.ts`, `update.ts` — the first-run steps, the statistics, meetings and transcripts, the quick panel and updates; described with their features below.
- `indicator.tsx` — the page of the indicator window (see `indicator.rs`): a capsule in the window's theme (level bars on a decibel scale, `meter`, and the clock while recording, the state while busy, a check on success) with the text of a problem, also in place of the check when the microphone went away midway or the text did not go to the history (`capsuleWarning`).
- `tray.tsx`, `quick.ts` — the quick panel (see `tray_panel.rs`): state and shortcut (`quickHead`: while recording, how to stop it, as the main card says; at rest `restingState` — "Not ready" with the reason when the main shortcut is not registered or the engine is missing, from `useStatus`, read again at every opening — and while working the phase with a lit dot), "Recognize again" after a failed dictation, recording a meeting (start and stop; `meetingFailureText`: a start or a stop the database refused says the meeting was not saved, not that it did not start or stop), the main hotkey's mode, microphone and model (`quickModels`: downloaded models and engines of connected services), the last text, the recent dictations (`get_history` with a `limit` of the few it shows), the day's statistics, a new version, "Open ahem" and "Quit".
- `i18n/` — i18next setup, `pickLanguage` (OS locale → supported language, English fallback), translations in `locales/*.json`; a test checks that every language has the same keys.

`components/`, by page:

- Dictation — `DictationPage.tsx`:
  - `OnboardingPanel.tsx` — first-run steps from `onboarding.ts` (the model, the permissions the OS asks for, the optional language model) checked from the app's state and `get_permissions`, read again every 2 s and on focus while shown; a permission's button calls `request_permission`; hidden by `onboarding_done`, which it sets itself once every step, the optional one too, is done.
  - `StatusPanel.tsx` — the dictation card, with a copy button when the text was not inserted (copied only on click; a copy the clipboard refused is said below the outcome, as in the history rows and the quick panel).
  - The pipeline of the main hotkey, whose processing tile opens the modes; "More shortcuts" — the other hotkeys from `shortcuts.ts`, each row opening its mode, or a line saying the selected text can be rewritten when no mode has a hotkey for it.
  - `StatsPanel.tsx` (see [History, statistics, indicator and tray](#history-statistics-indicator-and-tray)). The main mode is chosen in the editor of plain dictation and of the user's modes ("Make main"; not "In English", which is never the main mode) and in the quick panel.
- Transcripts — `TranscriptsPanel.tsx`: a card with "Record a meeting" and "Transcribe a file" — the file dialog, or a file dropped anywhere on the page — the list of meetings and files with their badge, and an entry's page; a screen chosen on the page puts the focus on its title, and every other screen starts at the top of the page (`drawnScreen`). `FilesPanel.tsx` is the file view of this page, kept while hidden: mode chips, format, progress, cancel, the saved file in its folder and "Open transcript", also for a transcript kept although its result could not be written (`FileEvent::Failed` with `transcript`); a result held after it could not be written (`held`) has "Save as…", which offers the file it was to go to, in its format (`heldDialog`, `save_held_result`); it says when the cloud engine cannot transcribe media files. `MeetingsPanel.tsx` and `SpeakerStages.tsx` hold the meeting parts (see [Meetings](#meetings)); an entry's page reads the entry again when its summary's state, title or saved file changes, so a file entry saved by "Save as…" loses "Not saved to a file" and shows its file.
- History — `HistoryPanel.tsx`: keep or not, how many and the file — show, delete — in its header, then the entries. "Last" chosen over "All" only shows its number, with the focus in it: Enter saves it, leaving the field saves only another number, and leaving without one or Escape goes back to "All" (`limitChoice`, `limitStep`, tested), so no dictation is deleted unasked. The field and its choice are one control: a number typed is saved by Enter or as the focus leaves the control inside the window, not as it goes to another window (`limitLeft`, `document.hasFocus`) nor to the choice — a press on the choice keeps the focus where it is — and "All" drops it, also while a number is being saved; a field that goes away with a refusal or "All" gives its focus to the choice. `useHistory` takes only the latest read's answer; the page, mounted while hidden, reads after a dictation or a change only once it is shown (`historyStep`, tested), and the quick panel reads its few entries (`limit`) whenever they change. Shown means the page open in a window its web view says is seen (`useWindowSeen`): on macOS a window hidden in the tray reads nothing after a dictation. The entries that a read on showing brings are there at once, unmarked (`catchUp`, `freshIds`, tested); only a dictation made while the page is seen grows in and lights up. The file's place is read without entries (`limit` 0) as the page is made, so its row is in the header before the first showing.
- Modes — `ModesPanel.tsx`: the list of modes and the editor of the chosen one; the editors are in `ModeEditors.tsx`.
  - Under each mode in the list, how it is started (`modeLaunch`: its hotkey, its selected-text hotkey, in how many programs the "by application" hotkey takes it).
  - Plain dictation has its clean text (`CleanTextSection`: off, filler sounds, or a language model with its model chosen like a mode's; the words to remove in a text field with a button that restores the basic set), its rules for programs and "Make main"; while it is the main mode, a note on the main hotkey (`plainModeNote`) instead.
  - What a mode does is one line of text, not switches. Custom modes are saved field by field, a new one once it has a model and an instruction; its model is preselected from the newest language-model mode, otherwise chosen by the user; without any service a new mode shows `ServiceList` to connect one.
  - Translation to English is a row of its own under plain dictation, also while it is off: `EnglishEditor` turns it on (`withEnglish`) and gives it a hotkey, both disabled while the dictation model does not translate (`translationWarning` says why). `choosableModes` leaves it out of the main-mode choices.
- Dictionary, Services, Models and Settings — all four pages are in `SettingsPanel.tsx`:
  - Settings (`SettingsPanel`), in three tabs: general — theme, interface language, start at login, the two update switches (see [Updates](#updates)), the version and, once the site is up, "Help and feedback" and "Support the project" rows that open the blocks `#help` and `#donate` of the project's site (`SITE_URL`, `HELP_URL`, `SUPPORT_URL` in `links.ts`, no language in the address: the site follows the browser; `linkTarget` hides a row whose address is empty, `PREVIEW_LINKS` previews one); keys — every hotkey in one list from `shortcuts.ts` (dictation: the main one, by application, to English, each own mode; then the selected text of the modes with a language model; then how a hotkey records), edited in the row, the modes' hotkeys being the same values as in their editors; microphone and sound — microphone, mute, the indicator on screen (`show_indicator`).
  - Models (`ModelsPage`): `ModelsPanel.tsx` with each model's languages, its author and license in the tooltip of its name (`modelCredit`), a hardware badge (`hardwareBadge`: the card it needs; "no card needed" for sherpa-onnx models, which run on the processor alone; "card optional" for llama.cpp models, which `llama-server` offloads to the card by itself), the place it is downloaded from under its description — the repository on Hugging Face or the release on GitHub, a link that opens that page (`modelSource`, made from the catalog's pinned `url`, tested for every model of the catalog) —, and their deletion (the model dictation uses too, after "Delete the model in use?": dictation moves to another downloaded model, or to none), `CloudPanel.tsx` (the cloud engines, chosen like a model, with the service's key added in the row), the spoken language limited to the engine's languages, unloading (not for a cloud engine), with a note when the model ignores the language, and the speaker models (`SpeakerModelsCard.tsx`, with the same source line from the `url` of its first model). A model whose download ended stays among those on this computer until the list read after the end comes (`settling` from `useModels`; a voice model keeps its disabled "Cancel" until `get_speaker_models` answers), so the row never jumps to "More models" and back; "More models" stays mounted (hidden when empty), so its open state and a download's error in it last. A new download says nothing until the server answers: after "Download" or "Resume" the row stays where it is, its button disabled and busy ("Connecting…") and its "Delete" disabled, as the download already holds the files, and an earlier failure is hidden, until the model's first event or the command's refusal (`useConnecting`, `heardFrom`, tested; the speaker models too).
  - Dictionary (`DictionaryPage`): the hint for the engine, with a note when the model ignores it, and `ReplacementsPanel.tsx`.
  - Services (`ServicesPage`): `ConnectionsPanel.tsx` — the named services with their speech and text capabilities, one key each (`ServiceList`; `ServiceKeyForm` adds one key elsewhere), own servers with an OpenAI-style API at their address, and `ChatGptRow` — first in the text services, marked recommended — ChatGPT through the account: "Continue with ChatGPT", the first-use notice, "Manage usage", sign in again, disconnect.

## Backend

### App shell and commands

- `main.rs` — started with `--sherpa-worker`, the app runs as its own sherpa-onnx worker; with `--server-guard`, as the guard of a local server (`engines/local_server.rs`); otherwise it runs the app. Both are checked before Tauri starts.
- `lib.rs` — the Tauri builder: the plugins — `global-shortcut` (press and release of a registered hotkey go to the orchestrator with its action), `single-instance` (a second launch shows the window; on macOS, where opening a running app from Finder, Spotlight or the Dock starts no second process, the system's reopen does it: `platform::reopened`), `autostart` (the login entry starts the app with `--hidden`, so the window, hidden in `tauri.conf.json`, is not shown; with "start at login" on the entry is written again at each start, with where the app is now: `refresh_autostart`), `opener` and `dialog` — the managed state, the orchestrator thread, hotkey registration at startup, engine shutdown on exit (the sound unmuted first; the engine's thread waited for at most 2 s, not through a request it runs: the engine processes end with the app; the orchestrator's thread waited for at most `QUIT_WAIT`, 5 s, so quitting never hangs on it). The main window is built in `setup` once the commands' state is managed (`"create": false` in the configs): Tauri builds the config's windows before `setup`, and the page calls commands as soon as it loads.
- `commands.rs` — the commands of the main window and the quick panel: `system_locales`, `get_settings`, `save_settings` (canonical hotkeys, mode checks, registration of the hotkeys — see [Modes and language models](#modes-and-language-models) —, validation, then the orchestrator gets the new settings; it also turns the login entry on or off and emits `settings-changed`), `get_status`, `set_hotkey_suspended` (no hotkey is registered while a new one is recorded), `get_last_result`, `retry_available` and `retry_dictation` (a dictation that could not be recognized keeps its recording in memory (the newest speech wins: a retry of an older recording that fails again does not replace a newer one) until a dictation started after the failure gives text — one without speech (a touch of the hotkey, credits Whisper invents) leaves it, and so does one already recording when it failed; the engine gives it back at 16 kHz with its error, `Message::Unrecognized`, and one that never reached the engine keeps the microphone's rate —; it is not held to the threshold of speech again; recognized again with the engine chosen now, its text goes to the history and the last result, not into a window; `DictationEvent::RetryAvailable` tells the interface), `list_input_devices`, `list_languages`, `list_models` (with whether the model's engine takes the dictionary and the spoken language), `list_cloud_engines`, `download_model` (a background thread, progress as events), `cancel_model_download`, `delete_model` (refused during its download or its deletion; deleting the dictation model first switches dictation to another downloaded model, or none; the files go on a blocking thread), `data_folders` and `open_data_folder` (through the opener plugin: the folders are opened; the history file is selected once it exists), `add_connection`, `remove_connection` (refused for a service a mode or the dictation engine uses), `refresh_connection_models`, and the commands named in the sections below. `save_settings` takes a catalog model or a cloud engine whose service is connected as `model_id`.

  Settings change only on the main thread. `save_settings` runs there; the background commands that change them (connections, `delete_model`) hand the change over with `on_main_thread` and wait for it off the async runtime. Saving rebuilds the tray menu and registers hotkeys, which need the main thread: a background thread that held the settings lock while waiting for it would freeze the app, since a command on the main thread may be waiting for that lock. `register_hotkeys` calls the plugin outside the `Hotkeys` lock for the same reason (on Linux the plugin's thread takes that lock to route a key press).
- `i18n.rs` — reads the tray menu strings from the web interface's translation files.
- `tauri.conf.json` — app name, identifier `com.useahem.ahem` (it defines the user data path and the macOS Keychain item), windows, and the content security policy of the built app: scripts only from the app, images from the app and `data:`, nothing loaded from elsewhere, the backend only through IPC. Styles allow inline ones (React's `style` attributes). `dangerousDisableAssetCspModification` keeps Tauri from adding nonces and hashes to the policy: with a nonce in `style-src` the webview ignores `'unsafe-inline'`, and React's inline styles would stop working; the pages have no inline scripts that would need one. Tauri sets the policy only on the pages of its own protocol, so it does not apply under `tauri dev`, where the windows load Vite's server directly.
- `Info.plist` — macOS keys merged into the app's `Info.plist` (and embedded in development builds): the microphone usage description, without which macOS refuses recording; the audio capture description for meetings; `LSEnvironment` `MallocSpaceEfficient=1`, so the allocator hands freed memory back to the system at once (not in `man malloc`; checked on macOS 27.2; a launch by the login agent runs the binary directly and goes without it, so a file's reading and a meeting's transcription also end with `platform::release_memory`). Local models run in processes of their own, so the setting matters for the app's own memory, such as decoded meeting tracks.
- `Entitlements.plist` — macOS release builds are signed ad hoc as the bundle id (`signingIdentity: "-"` in `tauri.macos.conf.json`, so the Accessibility permission matches the app) with the hardened runtime, which needs the audio-input entitlement before macOS asks for the microphone.

### Dictation orchestrator

`dictation/` — the orchestrator.

- `controller.rs` (its file job in `controller/file_job.rs`, its tests in `controller/tests.rs`): one thread, a message loop over `Message` (hotkey, settings, engine replies, transcripts, insertion results); it drives `HotkeyGesture`, `DictationSession`, `EngineLifecycle` and `Scheduler`, keeps the last transcription, emits `CoreEvent`s, wakes for level updates and the idle timer. Text goes only into the window focused at the hotkey press; with none, the dictation fails with `NoFocus`.
- `services.rs`: the `Services` interface and `RealServices` (microphone, mute with crash marker, an insertion thread that waits for the hotkey's modifiers to be released, model lookup). A file window of digital silence (`speech::digital_silence`: the zeros of a gap or of a silenced echo) goes to no engine: it is answered at once with no words.
- `engine_worker.rs`: the thread that owns the speech engine of the selected model — the `whisper-server` or `llama-server` process, sherpa-onnx in its worker process or a cloud service with the user's key: start, transcribe, stop. A request that fails because its process died — either server or the sherpa-onnx worker, also when a stream finishes — reports `Message::EngineCrashed`, and the process is forgotten.
- The controller picks a `SpeechEngine`: a model `Services::ready_model` found (`ReadyModel`: path and its `SherpaSpec` or `LlamaSpec`), or the cloud engine of `model_id` with its service's connection, whose key the engine's thread reads from the secret store when it starts (`StartCloud`: the first read after an update may wait on the system's password prompt, and the orchestrator does not wait with it; no key is the engine's failure). Settings that change the engine — another model, or the same cloud engine through another connection — start it again (`Restart`), so an old key is not used on. The credits filter follows the engine started last (`whisper_started`), not the one chosen since. `engine_available` is true for sherpa-onnx and cloud engines and needs the `whisper-server` program for Whisper and `llama-server` for llama.cpp models (`services::engine_installed`, which `get_status` uses for the chosen model too).
- `file_reader.rs` — see [Files](#files).

Live dictation with a streaming model: the controller starts a stream once the streaming engine it started is ready and runs the model chosen (`EngineRequest::StreamStart`; `open_waiting_stream`, so a model stopped while it loads types nothing and no other engine is ever kept for a stream), feeds `Recording::samples_since` every 0.2 s (`StreamFeed`, replies `LiveText`), feeds the rest and ends with `StreamFinish` (replies `Transcribed`; without the stream the whole audio is transcribed) or `StreamCancel`. For a plain mode, in toggle mode, after a tap in auto mode (`Gesture::Latch`) or when the held dictation hotkeys have no Ctrl, Alt or Win (`hotkeys::holds_shortcut_modifier`), `Live` in the session types the text's new part (`Services::type_live`, which waits only for Ctrl/Alt/Win to be released — `platform::shortcut_modifiers_down`; replies `LiveTyped`) one piece at a time; `begin_insert` waits for the piece in flight and inserts only what was not typed. Text goes in in the order the dictations were made: a later dictation types nothing, live or at the end, while an earlier one still has text to put in — one with a window to put it in (`typing_waits`, `resume_typing`), and one lock lets only one thread type at a time — a dictation, its live text, or a rewritten selection (`services::typing`).

### Core

`domain/` — the platform-independent core (named `domain` because `core` is Rust's built-in crate). Pure state machines: they take inputs and return events and effects; the shell performs the effects. Invalid inputs return `InvalidTransition` and leave the state unchanged; errors carry only names, never dictation text.

- `session.rs` — `DictationSession`: recording → transcribing → post-processing (optional) → inserting → inserted | discarded (too short, no speech) | failed. A session that does not insert (`SessionMode::insert` off: a recording recognized again) ends as kept instead of inserting. A failed language-model step inserts the transcript and emits `ProcessingFailed`. `InsertionProblem`: no focus, focus changed, blocked, no permission, other. `Finished` carries the result (inserted or not) for the last transcription and history.
- `engine.rs` — `EngineLifecycle`: unloaded → loading → ready → unloading. Work acquires and releases the engine; the unload policy (immediate, after idle, never) applies when nothing holds it. Effects: start/stop the engine, start/cancel the idle timer (stale timer tokens are ignored). `EngineInput::Restart`: after a model change (or another connection of the cloud engine) the running engine takes no new request (`restarting`: the controller tells the scheduler it is unavailable and opens no stream on it) and stops once the request at it is done (`EngineInput::Idle`) — so audio goes only to the engine the user chose. A stream open at it keeps it to the end of its recording (`SchedulerInput::EngineFinishing`: only that dictation goes to it), so text typed as it is spoken goes on; only local models stream. A file or a meeting track the new model cannot go on with (no word times, or no translation for a file being translated) stops at once with that problem (`FileProblem::NoWordTimes`, `NoTranslation`), and a meeting between its tracks stops with it when its next track is asked for (`start_file`); work still holding the engine (the rest of a file, a dictation) starts it with the new model; after a failed load, it starts with the new model at once. A crash of a ready engine that other work holds besides the request that crashed (`holds > 1`: another dictation, a file, or a window of a file that ended while the window was at the engine, which holds it until its answer) starts it again, and the request fails on its own. A crash with only that request holding the engine, or while it loads (a model that cannot load would loop), leaves it down, and the controller fails what waits for it (`fail_waiting`).
- `scheduler.rs` — `Scheduler`: one engine job at a time, dictation first, then a recording recognized again, then file chunks; a recording recognized again and file chunks wait while a dictation records or waits, so a long retry does not hold up a new dictation; a running job is never interrupted.
- `gesture.rs` — hold, toggle or auto from presses and releases: in auto mode a press shorter than 300 ms records until the next press, a longer one until the release; key repeat ignored; a mode chosen during a recording applies from the next one; new settings record in auto mode, a file saved before the choice existed keeps toggle.
- `events.rs` — `CoreEvent`, the typed JSON events for the UI, among them `ModelEvent` (download progress, finished, failed with a typed `DownloadFailure`) and `DictationEvent` (blocked with a typed reason, input level, and the events of the sections below). All events go to the UI as the Tauri event `core-event`.
- `modes.rs`, `services.rs` — see [Modes and language models](#modes-and-language-models); `clean_text.rs`, `app_rules.rs`, `context.rs`, `replacements.rs` — see their sections.

### Engines

`engines/` — speech-to-text engines and the language models that post-process their text.

- `local_server.rs` — what the two local servers share: `ServerProcess` (a child process with its output in the log, waited for until `/health` answers, ended when dropped; it runs under a guard — the app started with `--server-guard`, checked in `main.rs` like the sherpa worker — that ends the server as soon as its input, a pipe from the app, closes, so a crash or a forced quit never leaves a model in memory, and ends with the server's code, or `SIGNALLED` (128, said in the log) when the system ended it: `guard_exit`) and `Agents` (a quick client for `/health` and a patient one for requests, both without a proxy).
- `whisper_server.rs` — `WhisperServer`: starts `whisper-server` on a free 127.0.0.1 port with a random request path (it takes the port only after loading the model: should another program take it meanwhile, once more on another, `port_was_taken`), waits for `/health`, posts WAV to `/inference` (`verbose_json`), stops the process. `EngineClient` is the HTTP side, tested against a fake server.
- `llama_server.rs` — `LlamaServer`: starts the official `llama-server` build with the model and its projector on a free 127.0.0.1 port, one request slot with a 4096-token context, no web interface; a random key reaches it in `LLAMA_API_KEY` (inherited `LLAMA_*` variables are removed) and goes with every request. The WAV goes from memory to `/v1/chat/completions` as base64 `input_audio`, with the model's instruction if it has one, at temperature 0, at most 1024 answer tokens; the answer becomes a `Transcript`, and one cut at that length (a model repeating itself) is an error for a dictation of one request and an empty window, said in the log, for a window of a file, a meeting or a long dictation (`recognize`, `recognize_window`) (`qwen3_asr`: `language <Name><asr_text><text>`). A dictation longer than a file window is sent in `files::chunks` windows and joined with `files::words::merge`. The models give no word times, so file windows get estimated ones: each word gets a share of the window's speech frames (`audio/speech.rs`) by its letters and digits, laid out like whisper-server's `verbose_json`. `LlamaClient` is the HTTP side, tested against a fake server.
- `cloud.rs` — cloud recognition: three services (Groq `whisper-large-v3`, OpenAI `gpt-transcribe`, Deepgram `nova-3`) and `CloudClient` — Groq's Whisper API (`transcriptions` or `translations`, `language`, `prompt`, word times for files with the punctuation taken back from the full text), `gpt-transcribe` (`languages[]`, `keywords[]`; no translation and no word times, so no media files) and Deepgram's `listen` (`language` or `multi`, `keyterm`); file words come out like whisper-server's `verbose_json`. `check_deepgram_key` checks a Deepgram key. Errors carry statuses and fixed texts only.
- `sherpa.rs` — `SherpaEngine`, the recognizer the sherpa-onnx worker runs: an offline (Parakeet, GigaAM) or online (Nemotron) transducer from the `sherpa-onnx` crate, on the processor with the engine's thread count. Audio goes in at 16 kHz; the online model gets 0.3 s of silence in front, 1 s after, and the spoken language as its `language` option. Dictation gets a `Transcript` — an offline model's dictation longer than a file window in windows joined as a file's (`files::chunks`, `files::words::merge`): in one pass the model gets worse towards the end and its attention grows with the square of the length; file windows get tokens joined into words and laid out like whisper-server's `verbose_json`, so `files::parse_words` reads both engines. A streaming model also takes a dictation while it is recorded: `LiveStream` (`start_live` / `feed_live` / `finish_live`) gets the samples at the microphone's rate and returns the text so far.
- `sherpa_process.rs` — the sherpa-onnx worker: the app started with `--sherpa-worker` (`main.rs` checks it before Tauri) loads the model and answers over stdin/stdout — a JSON line per message, then the samples as little-endian `f32`. `SherpaProcess` (the engine thread's handle) loads, transcribes, gives file windows' words, streams a dictation and stops by closing the input (killed after 2 s); a dead worker is reported as `EngineCrashed`. `diarize` runs the speaker models in a one-off worker, which sends progress lines (`Reply::Progress`: the first at once, then one per whole percent) before its answer. Unloading ends the process, so all of a model's memory goes back to the system. A thread passes the worker its input, and the end of it ends the process at once, also in the middle of a request (`input_ending_the_process`): the app keeps the input open while it waits for an answer, so a worker never outlives the app.
- `languages.rs` — Whisper's languages: codes and the English names `whisper-server` reports, and the other names engines give one of them (Qwen3-ASR's Filipino for Tagalog).
- `hallucinations.rs` — see [Recognition quality](#recognition-quality).
- `llm/` — see [Modes and language models](#modes-and-language-models); `chatgpt.rs` — see [ChatGPT through the account](#chatgpt-through-the-account).

`whisper-server` and `llama-server` are separate programs; the app looks for them in `runtimes/` of the source tree (see [Development files](#development-files)). sherpa-onnx is linked into the app's executable.

Logs are in `<app local data>/logs/`: `engine.log` gets the output of the speech engine's process (whisper-server, llama-server or the sherpa-onnx worker) and of the guard of a local server, which says when the system ended the server; it is started over at each start by `local_server::open_log`, which keeps the last start's log as `engine.previous.log`, so the reason for a crash survives the restart that follows it; `speakers.log` gets the output of the worker that tells voices apart; `app.log` gets what the app itself says on standard error with `log_line!` (problems it gets over: a window's answer cut at its length, a meetings database it cannot compact — never a key or a dictated text) when it is a release build started without a terminal, whose standard error would go nowhere (`log_to_file` in `lib.rs`, `platform::redirect_stderr`: `dup2`, `SetStdHandle` on Windows), the last run's kept as `app.previous.log`; in development and from a terminal it stays on the terminal. `src-tauri/clippy.toml` refuses `eprintln!` and `eprint!`, which panic when standard error cannot be written.

### Audio

`audio/`:

- `capture.rs`: microphone capture with cpal on its own thread (any device and sample format, channels averaged to mono, input level for the indicator). A device that fails during a recording (a headset gone; an overrun or underrun is only a glitch) keeps what was recorded before it, and only a recording with nothing in it is an error; the controller then emits `DictationEvent::MicrophoneLost`: what came before is recognized, and the main window, the quick panel and the capsule say so.
- `resample.rs`: conversion to 16 kHz with a windowed-sinc low-pass filter; `Resampler` does the same block by block, for meeting tracks and decoded files (`files/decode.rs`).
- `ogg_opus.rs`: `OggOpusWriter` — 16 kHz mono as Ogg Opus through libopus, 24 kbit/s, a page a second.
- `wav.rs`: 16-bit mono WAV in memory.
- `output.rs`: the default output's format, to tell when a headset is back from its headset mode.
- `mute.rs`: `MuteGuard` over a `SystemOutput` — mutes the default output only when its sound was on and unmutes that same device even when another became the default meanwhile (a device gone by then is forgotten); a marker file with the device's id is kept while muted, and the next start after a crash unmutes that device.
- `speech.rs` — see [Recognition quality](#recognition-quality).

### Platform layer and hotkeys

- `hotkeys.rs` — parsing and the canonical stored form of hotkeys; registration is in `commands.rs`. The default main hotkey is `platform::DEFAULT_HOTKEY`: `Alt+Space` (Option+Space) on macOS, where Control+Option+Space selects the next input source, and `Ctrl+Alt+Space` on Windows and Linux.
- `platform/` — all OS-specific code; other modules call its functions, and an OS without an implementation answers "unsupported", so the app builds everywhere. Outside it only tests are chosen by OS (one that needs the Keychain, or a Unix shell).
  - `mod.rs`: the backend chosen per OS and what the backends share:
    - `FocusTarget` (the foreground window and its program; `same_place`: the same program and window, where a window 0 — not read: no Accessibility permission on macOS, or no answer — matches any window of that program), `InsertError`, `SelectionError`, `Permissions` (microphone and Accessibility: granted, missing or not needed on this OS; `request_permission` shows the OS's prompt or returns its settings page, which the command opens);
    - `wait_for_copy`, the copy of the selection on macOS and Windows: presses the copy shortcut, waits up to 0.5 s for the clipboard to change and reads it, then puts the earlier clipboard back; when nothing came in time, a watcher puts it back after a late copy for 2 s more, unless a newer copy has started (each copy is a generation of `COPIES`). A clipboard a password manager marked private is checked before the copy (the OS side copies nothing then) and after it (`read` gives nothing);
    - the defaults and measures that differ per OS: `DEFAULT_HOTKEY`, `UI_ZOOM`, `TRAY_ICON`, `TRAY_PANEL_LEFT_OF_ICON` (the quick panel's left edge 5 pt left of the icon on macOS, as the menus', `None` for centered elsewhere) and `TRAY_PANEL_MARGIN` (the transparent margin around the panel in its window, as in `tray.css`: 1 px on macOS for its hairline, 16 px elsewhere to keep off a taskbar and the screen edges), `INDICATOR_MARGIN` (the indicator over the bottom of the work area: 10 pt on macOS, whose work area ends above the Dock, 48 px elsewhere), `BROWSER_ARGS` (the WebView2 arguments every window must get alike, as they share one browser environment: wry's defaults and grayscale text antialiasing; other OSes ignore them);
    - the computer's sound for meetings (`SystemAudio`, `open_system_audio`, `system_audio_supported`; see [Meetings](#meetings)), `set_in_dock` (macOS: in the Dock only while the window is open), `frontmost_program` and `give_focus_back` (macOS: the program in front before the quick panel gets the focus back when it is put away), `build_floating` and `focus_panel` (macOS: the capsule and the quick panel act as panels that do not activate ahem, as the menus of the menu bar — on every space, over full-screen programs also while ahem is in the Dock, and the panel takes the keyboard without bringing ahem forward, which would leave the full-screen program. AppKit decides by `_isNonactivatingPanel`, yes only for an `NSPanel` made so; `tao` makes an `NSWindow` whose class cannot be swapped, key-value observers are tied to it, and AppKit asks once, when the window is made. So NSWindow's `_isNonactivatingPanel` answers yes for `tao`'s windows while `build_floating` makes one and for the windows made so, and AppKit's own answer for all others), the free space for downloads (`available_space`: as Finder counts it on macOS, otherwise by `fs4`), and starting console programs without a window (`hide_console`).
  - `keys.rs`: text as key strokes (UTF-16 units, line breaks as Shift+Enter: a new line in chats, where Enter sends).
  - `win32.rs`: `SendInput` in batches with UIPI detection and the foreground window checked again before each batch (moved away: `InsertError::Interrupted` with the bytes typed, `keys::typed_len`, so live typing does not type them twice), the focused window, its process and program file, modifier state, playback device mute by endpoint id (`DefaultOutput`: the default device's id, a device gone or unplugged left alone), the microphone switches of the privacy settings (`ConsentStore\microphone`: device, apps, desktop apps), the clipboard.
  - `win32_selection.rs`: reading and replacing the selected text through UI Automation.
  - `win32_secrets.rs`: DPAPI for keys.
  - `macos.rs`: `CGEvent` key events with Unicode text, at most 20 UTF-16 units each and surrogate pairs kept together, Shift+Return for line breaks, other modifier flags cleared, and before each event `keys_left` checks that the keys still go where the focus target is (the program in front, or ahem's quick panel while it has the keyboard). The focus target is the frontmost application (`NSWorkspace`, no permission needed) and, with the Accessibility permission, its focused window (a hash of its Accessibility element); without the permission insertion returns `InsertError::NoPermission` and asks macOS once per run to show its own prompt. The permission is checked with `AXIsProcessTrusted` only, which macOS answers anew each time (`CGPreflightPostEventAccess` keeps its first answer until a restart); the microphone permission comes from `AVCaptureDevice` (AVFoundation), asked for by opening the microphone until macOS has the answer; modifier state from `CGEventSourceFlagsState`; mute through Core Audio's `kAudioDevicePropertyMute` of the default output, kept by its UID (`kAudioDevicePropertyDeviceUID`, found again with `kAudioHardwarePropertyTranslateUIDToDevice`; a device without the property or gone is left alone); the clipboard through `NSPasteboard`; the free space as Finder counts it (`important_capacity`: `NSURLVolumeAvailableCapacityForImportantUsageKey`); the capsule and the quick panel as panels that do not activate ahem (`make_floating`, `is_floating`: NSWindow's `_isNonactivatingPanel` answered yes for them), and while the panel has the keyboard insertion takes ahem for the program in focus (`set_panel_keys`, `keyboard_process`), and a window of ahem is never an unknown one — the panel (`PANEL_WINDOW`) or any other of its windows (`OWN_WINDOW`, not asked of Accessibility, which would wait for ahem's own main thread) — so a text meant for one never goes into the other (`keys_left`, tested, checked before every key and before ⌘C); neither window hides with "Hide ahem" (`setCanHide(false)`).
  - `macos_selection.rs`: reading and replacing the selected text through Accessibility (`AXFocusedUIElement`, `AXSelectedText`, `AXSelectedTextRange(s)`), by the same rules as on Windows (`check`, tested); the replacement is typed over the selection.
  - `macos_secrets.rs`: a random 256-bit key in the login Keychain (service = the app identifier), each secret sealed with AES-256-GCM by `ring` (format byte, nonce, ciphertext); `secrets.json` keeps its shape.
  - `macos_tap.rs`: the computer's sound for meetings (see [Meetings](#meetings)).
  - `unsupported.rs`: Linux and other systems — no insertion, selection, secret storage or permissions; the app runs, but dictation cannot type into other programs.

### Storage and downloads

- `util.rs` — small helpers the whole app shares: `now_ms`, `hex`, `base64` and `base64url` (with `from_base64url`), `random_bytes`, `random_hex` (request paths, keys, ids).
- `storage/mod.rs` — what the stores share: `migrate_sqlite` (the history, statistics and transcripts files upgrade step by step in one transaction, a newer file refused), `sqlite_code` (an SQLite error by its code only: its message could quote the data) and `write_whole` (settings, keys, model markers, exported transcripts and replacements through a temporary file flushed to the disk), `remove_sqlite_files`.
- `storage/settings.rs` — `settings.json` in the app config directory with `schema_version` and step-by-step migrations (version 2: plain dictation loses its own hotkey, `english` stays only with a hotkey or as the main mode); atomic writes. A broken or newer file is never overwritten: defaults are used and saving is disabled. Values a file edited by hand brings out of range are brought back (`repair`, in memory until the next save): hotkeys, languages, limits — a history larger than the largest choice keeps that many —, a model no longer known, and modes no save would pass (a missing or changed built-in, a repeated or unusable mode, an unknown main mode, a hotkey used twice), so saving goes on.
- `storage/secrets.rs` — `SecretStore`: keys in `secrets.json` next to the settings, each sealed by `platform::protect` (DPAPI on Windows, AES-256-GCM with a Keychain key on macOS). The interface sees only `key_hint`. A damaged file (not JSON) holds no key that could still be read: the next key saved starts it over. JSON of another shape was written by a newer version (a version field, keys of another form): it is never written over, and saving a key fails instead.
- `storage/catalog.rs` — the model catalog `resources/models.json` (embedded). Each entry has:
  - a pinned URL, size and SHA-256; whether Whisper translation works; its languages (`ModelSpec::languages`: its own list, as GigaAM's Russian, or without one every language of `engines/languages.rs`); what it needs to be fast enough (`Hardware`: a graphics card with at least N GB, or the processor alone);
  - for sherpa-onnx models a `SherpaSpec` (recognizer: offline or online transducer, `model_type`, the four file names inside the archive);
  - for llama.cpp models a `LlamaSpec` (the projector `mmproj` with its own URL, size and SHA-256, how the answer carries the text: `text` or `qwen3_asr`, an optional instruction).

  Sources are checked per entry: Whisper `.bin` only from `huggingface.co/ggerganov/whisper.cpp/resolve/<40-character commit>/`, sherpa-onnx `.tar.bz2` only from `github.com/k2-fsa/sherpa-onnx/releases/download/asr-models/`, llama.cpp `.gguf` and its projector only from `huggingface.co/ggml-org/<repository>/resolve/<40-character commit>/`, both from the same repository and commit. `download_size` adds the projector to the model's size for the interface. Ids have no dots (they are i18n keys). Listed from the most demanding model to the lightest; the interface keeps this order. Validated by a test.
- `storage/models.rs` — `ModelStore`: `<app local data>/models/<id>/<file>` plus a `ready.json` marker (SHA-256, size, mtime) written after verification; states missing / partial / ready (a whole sherpa-onnx archive without a marker — the disk had no room to unpack it — is partial: it can be unpacked again or deleted). A download first checks free space for all of it at once, half as much again as an archive for its unpacked files included (`space_needed`), and reports where it starts, so a whole file only checked and unpacked is not silent. A file copied in by hand is verified by hash instead of downloaded again; a file cut short while unpacking is deleted. A sherpa-onnx archive, once its hash matches, gives up only the four listed files from its top folder (`tar` + `bzip2`), the marker records their sizes and times, and the archive is deleted; `ready()` returns the folder. A llama.cpp model downloads the model and then its projector into the same folder, reported as one download; the marker records both, and `ready()` returns the model file with the projector next to it. `delete` removes a model's folder.
- `storage/history.rs`, `storage/stats.rs` — see [History, statistics, indicator and tray](#history-statistics-indicator-and-tray).
- `runtimes/http.rs` — the shared `ureq` agent: rustls with ring, OS certificate verification; `parse_json`, a service's JSON answer whose error says where it broke, never what it held.
- `runtimes/download.rs` — `unpack_named` takes named files out of a `.tar.bz2` (only from its top level or single top folder: a same-named file deeper inside cannot stand in), for the models and the voice models; resumable downloads to `<file>.part` with `Range`, free-space check (`platform::available_space`: on macOS with what the system frees on demand, as Finder counts it), size and SHA-256 verification, cancel. A server file of another size than the pinned one (by `Content-Length`, the total in `Content-Range`, or a 416 for a part past its end) deletes the part: it can never become the expected file.
- `runtimes/test_server.rs` — a tiny HTTP server on 127.0.0.1 for tests.

## Modes and language models

- `domain/modes.rs` — `Mode` (built-in `plain`, always there, and `english`, there only when the user turns translation on (`english_mode`); the user's language-model modes with a connection, model, instruction and output language), `Connection` (a service without its key; `ProviderKind::Deepgram` recognizes speech only), `hotkey_actions` (checks the modes — a mode needs a connection with language models — and maps the main hotkey to `Main` (always the main mode), the "by application" hotkey (`Settings::app_hotkey`, unset by default) to `ByApp`, and every other hotkey to `Dictate { mode_id }` or `Rewrite { mode_id }`; the translation hotkey (`engines::translates`) is registered only while the dictation model translates), `mode_using`.
- `domain/services.rs` — the named services (`Service`: Anthropic, OpenAI, DeepSeek, Groq, Deepgram) and `Service::of` for a stored connection; shared by the language-model connections and the cloud engines.
- `commands.rs` keeps the registered hotkeys in `Hotkeys` (shortcut → action), shared with the plugin handler in `lib.rs`. `register_hotkeys` registers the wanted set in place of the current one, given the hotkeys the user already had (`known`; `register_with` is its part without the plugin, tested): a hotkey of `known` that another program holds is left out and the rest registers — it was taken before, and refusing for it would refuse every save —, while a newly chosen hotkey that is taken refuses the save (`SaveError::HotkeyTaken`) and the previous set stays registered. One hotkey for two actions of the settings is refused the same way (`wanted_hotkeys`), any other error of the modes as `SaveError::Invalid("modes")`, which the interface never sends. At startup and when a recorded hotkey ends, every hotkey that is free is registered (`register_startup_hotkeys`; settings with no valid set, edited by hand, fall back to the main hotkey), and `get_status` lists the rest as unregistered. While a hotkey field records a new one (`set_hotkey_suspended`), none is registered: `save_settings` only tries the newly chosen hotkeys (`try_hotkeys`: each registered for a moment and let go), and `get_status` names the ones that were taken when the pause began (`TAKEN_WHEN_SUSPENDED`). The end of the pause registers them again and emits `hotkeys-changed`, on which the main window reads the status again. `save_settings` keeps the stored connections, so only `add_connection` (checks the key by listing the models, stores the key encrypted), `remove_connection` (refused while a mode uses it), `replace_connection_key` (a new key, checked the same way, in place of an expired one: the connection and the modes that use it stay; a refused key leaves the old one) and `refresh_connection_models` change them.
- `engines/llm/` — the language models:
  - `mod.rs`: `Provider::of` a connection (none for Deepgram), `process`, `list_models` (the list leaves out speech, image, embedding, moderation and legacy completion models by their ids), `checked_base_url` (HTTPS, or plain HTTP only to this computer).
  - `anthropic.rs`: the Anthropic Messages API and its model list.
  - `openai.rs`: the OpenAI Responses API, OpenAI-compatible Chat Completions and their shared model list.
  - `prompt.rs`: the protective system prompt; the text goes as delimited data under it.
  - `tests.rs`: requests and replies of all three APIs against a fake server.

  Errors carry only statuses and provider error codes, never the key, the text or a response body; redirects are not followed.
- The orchestrator: a language-model mode moves the session through post-processing (`Services::process` on its own thread); a failure inserts the transcript. A `Rewrite` hotkey calls `Services::rewrite_selection` (`platform/win32_selection.rs` through UI Automation on Windows, `platform/macos_selection.rs` through Accessibility on macOS; unsupported on Linux): read the selection, process it, replace it only if the selection is unchanged; one rewrite at a time, reported as `selection_*` events.

## History, statistics, indicator and tray

Its page holds the widest and the tallest capsule (three lines of a problem), zoomed as the page is (`UI_ZOOM`), and the capsule's middle keeps its place above the work area's end (`position`, tested), on the monitor under the mouse — on macOS found and placed in points (`platform::PLACES_IN_POINTS`), so a second screen of another scale gets it. ## Files

- `files/` — `decode.rs` (`symphonia`, Opus through libopus: the first audio track as 16 kHz mono, block by block, through `audio::resample::Resampler`), `chunks.rs` (windows of up to 32 s cut at the quietest 200 ms between 25 and 30 s, 2 s of context on each side; `Planner` works on a stream), `words.rs` (`parse_words` from the engine's one-word segments, `merge` matches the transcripts at each seam by a common run of words and falls back to word midpoints; `without_credits` drops Whisper's invented credits from a window's own part; paragraphs and subtitle cues), `export.rs` (TXT, Markdown, SRT, WebVTT, JSON).
- `dictation/file_reader.rs` — a thread per file: decodes and cuts the next window on request, so about one window of audio is in memory. A panic in the decoder (a damaged file) fails the file (`FileReadFailed`); release builds unwind (`panic = "abort"` is off), so a panicking thread never closes the app.
- The orchestrator keeps one `FileJob`: it holds the engine for the whole file, queues each window in the `Scheduler` (dictation first; a finished recording is queued before `RecordingEnded`, so a waiting window never goes ahead of it), asks the reader for the next window while the engine works, merges and exports, or sends the text to the mode's language model (Markdown or text only; on failure the transcript is saved). A `.txt` file goes straight to the language model. Typed `file` events report progress and the outcome.
- `engines/whisper_server.rs` asks for word times when `TranscribeOptions::words` is set (`files::WORD_TIMESTAMP_FIELDS`); `engine_worker.rs` answers `TranscribeChunk` with the raw JSON. llama.cpp models answer with estimated word times (`engines/llama_server.rs`), so their subtitle times are approximate.
- Commands `transcribe_file` (checks the mode, format and folder; refuses audio and video for a cloud engine without word times; reads a `.txt` up to 1 MB) and `cancel_file`; the interface uses the dialog plugin to choose the source and the destination.
- Kept transcripts: once an audio or video file's result is written, the controller hands `Services::keep_transcript` a `FileTranscript` — the words as turns (`FileJob::turns`, by speaker when the voices were told apart), the length, the source and output paths, the language model's text (`FileJob::processed`) — and `RealServices` adds it to the meetings store as a `file` entry; `FileEvent::Finished::transcript` carries its id. A `.txt` file is not kept; a failure to keep it leaves the saved file as the result. A result that cannot be written (a drive gone, a full disk) is kept all the same, with no output path, and `FileEvent::Failed::transcript` names the entry; as the list may be on the full disk too, the controller also holds the result in memory until the next file (`held_result`, `FileEvent::Failed::held`), and `save_held_result` takes it (`Message::TakeHeld`) and writes it where the user chooses, off the orchestrator's thread, making that file its entry's saved file. "Save as…" of a file entry with no saved file makes the chosen file its saved file (`Meetings::file_saved`), and of a file processed by a language model writes the model's text in Markdown and plain text (`files::export::processed_export`).

## Meetings

Meetings and files share one list of transcripts.

- `meetings/track.rs` — `Track`: one source (`Source::Microphone` — the microphone of the settings while connected, else the default — or `Source::System`, the computer's sound) recorded on its own thread into Ogg Opus; every 0.5 s it checks which device should be recorded and reopens the stream when that changed or failed (an overrun or underrun is a glitch, not a failure: `audio::capture` skips it); `timeline.rs` (`Timeline`) fills gaps over 0.2 s with silence by the wall clock, so both tracks stay aligned across device switches and silent Windows loopback. Why a track records nothing goes out with the meeting's status (`TrackProblem`: no device, or its file cannot be written).
- `platform::open_system_audio` — macOS: a Core Audio tap of every process (`CATapDescription` global, unmuted, private) behind a private aggregate device that cpal records (`platform/macos_tap.rs`); Windows: WASAPI loopback of the default output through cpal; Linux: unsupported. `build.rs` links Core Audio weakly on macOS, so the app starts before macOS 14.2; `platform::system_audio_supported` tells the page.
- `meetings/store.rs` — `MeetingStore`: `<app local data>/meetings.sqlite3` (id, start, duration, title, state, problem code, turns as JSON, preview; since schema version 2 also `kind` — `meeting` or `file` — and a file's `source`, `output` and `processed` text; schema version 3 adds `folder`, the name of a meeting's folder; versions upgraded step by step in one transaction, a newer file refused).
  - A meeting's audio: `meetings/<local date and time it started, "2026-11-10 15-26", " (2)" … when taken>/me.opus`, `others.opus` and, once a transcription has started (mixed before the tracks are recognized, and kept if it fails or is stopped), `call.opus` (`meetings/mix.rs`: both tracks summed, the microphone without the echo where it was silenced; "Show audio file" shows it, else `me.opus`). Folders of older meetings, named by their id, are renamed when the store opens.
  - A file entry has no folder and points to the user's file; deleting it leaves the user's files.
  - Entries are kept until deleted; `secure_delete` and temporary data in memory as in the history, and a store that finds free pages (deleted before that) runs `VACUUM` when it opens, if it can (`compact`); meetings left recording or transcribing rest at the next start: "done" with a transcript, else "recorded" (`rest`, also only if the file can be written: on a full disk the meetings still open, to be deleted to make room, and the list shows those left going as resting until one is worked on again; so does a meeting whose end — recorded, transcribed, failed or stopped — could not be written while the app runs, so it can be transcribed again). A folder named by its number (meetings recorded before dated folders) gets its date when the database has taken the new name, so a database that cannot be written leaves it where its meeting finds it. `Meetings::transcribe` refuses a file entry (`NotAMeeting`).
- `meetings/service.rs` — `Meetings` (managed state): one recording (two tracks, a status thread emitting `MeetingEvent::Recording` five times a second) and one transcription on a worker thread (a panic in it — a decoder on a damaged track — fails the meeting with `read` and frees the slot, `guarded`). Each track goes to the orchestrator as a `FileRequest` with `reply`, so the controller sends back `TrackUpdate`s (progress, the words with the replacements, failure, cancel) instead of saving and emits no `FileEvent`s for it; then `speakers.rs` tells the voices of the computer's sound apart. While recording, `RealServices` skips "mute while recording". The length of a meeting is saved every 5 s while it records. A stop tells the interface `Recorded` also when the database cannot take its end (a full disk), and returns that error after it; quitting waits for a stop or a discard on its way (`ending`).
- `meetings/speakers.rs` — telling the voices apart, in a one-off sherpa-onnx worker:
  - sherpa-onnx's offline speaker diarization through its C API with the progress callback, which the `sherpa-onnx` crate does not pass on; pyannote segmentation 3.0 + 3D-Speaker ERes2NetV2, the segmentation window moved by a fifth of its 10 s, all threads but one, cluster threshold 0.67, a voice heard for under 1.5 s goes to the nearest longer one;
  - voices whose average embeddings (`SpeakerEmbeddingExtractor`, stretches where the voice speaks alone) are 0.71 alike or more are joined, the most alike first, keeping the number of the one heard longer, and a voice with too little speech alone to know its sound goes to the voice its segments sound like;
  - then, given the track's words, `transcript::sentences` cuts them into sentences and each sentence of 0.6 s or more takes the voice whose average embedding is closest, so the segments returned are one per sentence, meeting halfway between their words;
  - progress: `MeetingEvent::Progress` gets step `segments` (the segmentation model, which tells no progress) and, from the first share the worker sends, step `voices` with the second model's share as milliseconds of the recording (its pass in sherpa-onnx as the first three quarters, then joining and sentences); the interface shows a bar for each model (`SpeakerStages`), the first one running without a measure;
  - models in `<models>/speakers`, pinned size and SHA-256, downloaded on request with `ModelEvent`s as `speakers`.
- `meetings/transcript.rs` — gives each word of the computer's-sound track the speaker of the shortest segment covering the middle of where it is spoken (`voice_at`), groups each track into turns (pause under 1.5 s) and orders them by start; exports TXT and Markdown with time and speaker, SRT and WebVTT cues with the speaker, JSON with turns and words.
- `meetings/echo.rs` — a meeting recorded from speakers: `find_echo` (delay and level of the others in the microphone, from 10 ms frame levels where the others speak — above their silence, measured where anything sounds, so digital silence before a call does not make the noise of an open microphone their speech; none with headphones), `echo_mask` and `gate` silence the echo in a copy of the microphone track (`me-without-echo.opus`, deleted after its transcription), `drop_echo_words` removes the user's words that repeat the others' at that delay.
- Files by speaker: with the speaker models downloaded, `transcribe_file` takes `speakers` (the names, `transcript::Labels`) for audio and video; after the merge the controller emits `FileEvent::Speakers` with step `segments`, then `voices` with how far (as `done_ms` of `total_ms`, the file's length) and asks `Services::diarize_file` (a thread: `SpeakerModels::diarize` with the file's path and the merged words — the worker reads the file itself —, the share done as `Message::FileDiarizing`, then `Message::FileDiarized`); with two voices or more the file is saved by speaker (`transcript::export`) or the mode's language model gets "Speaker 1: …" lines; otherwise, or when telling apart fails, as without speakers.
- Cancelling: `Message::CancelFile` (the file view) and `Message::CancelTrack` (a meeting) each cancel only their own kind of job; a meeting track that finds the orchestrator busy with the user's file waits 2 s and tries again (a busy slot is no meeting problem). A track that cannot write (a full disk) reports the problem and stops writing.
- `meeting_commands.rs` — the commands that wait on the disk or the tracks' threads (`get_meetings`, `get_meeting`, `start_meeting`, `stop_meeting`, `discard_meeting`, `transcribe_meeting`, `delete_meeting`, `rename_meeting`, `export_meeting`, `delete_speaker_models`) run on a thread for blocking work (`blocking`: off the main thread and the async runtime's); `get_meetings`, `get_meeting` (with the path of `call.opus`, else of the microphone track, for "Show audio file"), `get_speaker_models` (the Models page; `partial` when a stopped download left files, which can be deleted or resumed), `start_meeting`, `stop_meeting` (keeps the recording and starts its transcription when the chosen engine can transcribe it, by the same check as `transcribe_meeting`; else it stays recorded), `discard_meeting`, `transcribe_meeting` (refused at once, before the echo is found and the tracks mixed, without a chosen model, without its engine, or with a cloud engine that gives no word times: `no_model`, `no_engine`, `no_word_times`), `cancel_meeting_transcription`, `delete_meeting`, `rename_meeting`, `export_meeting` (the names of the speakers come from the interface; a file entry whose voices were not told apart is saved as the file view saves it, `transcript::export_file`), `download_speaker_models`, `delete_speaker_models`.
- Interface: `components/SpeakerModelsCard.tsx` on the Models page (what is downloaded, its size, download, delete; `useSpeakerModels`, also for the "By speaker" option of the file view); `components/MeetingsPanel.tsx` — the parts of the Transcripts page: `useMeetings` (the list, read again on meeting events and when a file's transcript is kept), `RecordRow` (a clock and a level strip per track while recording, and why a track records nothing: no device, or not being saved, `TrackProblem`), `MeetingRow` (title, "meeting" or "file" badge, length, state, preview), `MeetingView` (an entry with its turns, copy, save as, rename, delete; a meeting can be transcribed again and shows its audio; a file shows its source, its saved result or that it was not saved to a file (`unsavedFile`), and the processed text, and its turns have no speaker name when its voices were not told apart) — and `meetings.ts` (types, `reduceMeeting`, clock, speaker names: a file's voices are named as on the file view).

## Recognition quality

`audio/speech.rs` estimates how much of a recording is speech by loudness (20 ms frames, noise floor from the quietest frames); a session with less than `MIN_SPEECH` (0.2 s) is discarded as no speech without reaching the engine. `engines/hallucinations.rs` drops transcripts of Whisper (on this computer or at a cloud service) that are exactly a known invented credit line — a dictation, and the own part of a window of a file or of a meeting track (`files::without_credits`), whose own words then go while the words it shares with a neighbour stay for the seam (a microphone track with the echo silenced is mostly such windows); other engines do not invent them, and such a line from them is kept (`SpeechEngine::is_whisper`).

The spoken language (`None` = detect) and the dictionary reach only the engines that take them (`ModelSpec::takes_dictionary` and `takes_language` in `storage/catalog.rs`, every cloud engine takes both; the Models and Dictionary pages say when the model ignores them). `whisper_server::prompt_from_dictionary` makes one prompt of the dictionary's terms (separated by commas, semicolons or new lines, also as Chinese and Japanese keyboards type them), whole terms only, up to 600 units — rough thirds of a token: a character counts one, one of three or more bytes in UTF-8 (Chinese, Japanese, Korean, Devanagari, Thai and the like) three, as it is a token or more (`whisper_server::units`):

- Whisper — whisper-server and Groq's `whisper-large-v3` — gets the language (`auto` without one; none to Groq for a translation, which is always English) and the dictionary as `prompt`, cut again to whole terms up to 300 units (`whisper_server::whisper_prompt`: Whisper reads only the last 223 tokens of a prompt, so a longer one would lose its first terms).
- `gpt-transcribe` gets `languages[]` and the terms as `keywords[]`; Deepgram gets `language` (`multi` without one) and the terms as `keyterm`; both at most 100 terms of the 600-unit prompt.
- sherpa-onnx takes no dictionary, and only the streaming model (Nemotron) takes the language: Parakeet detects it itself, GigaAM knows only Russian.
- llama.cpp models take neither; they detect the language.

## Muting

Opening a headset's microphone switches a wireless headset into its headset mode, which silences it for a moment and makes music muffled. So "mute while recording" (on by default) mutes the default output (`audio/mute.rs`) at the press, just before the microphone opens. Before it opens the controller notes the default output's device, rate and channels (`audio/output.rs`); after it closes, if the format is still another one (the headset is in its headset mode), the sound waits for the headset (`restoring`).

Measured with AirPods on macOS (`headset_timeline`, an ignored test in `platform/macos.rs`): the headset mode holds about 2.2 s after the microphone closes, the format comes back at the start of the switch, and the sound plays again 0.6–1.1 s later; so the sound returns 1.3 s after the format is back, at most 5 s after the microphone closed.

A new dictation in the meantime opens the microphone without a switch: muted sound stays muted, and the format from before is kept to wait for.

## Clean text

`domain/clean_text.rs`, `Settings::clean_text`: how plain dictation cleans its transcript — off, filler sounds removed (the default), or a language model.

- `remove_fillers` drops the words of `Settings::fillers` — comma-separated, shown and editable in the interface, starting as `DEFAULT_FILLERS`: sounds that are words in no language written with these letters ("э-э", "эм", "uh", "hmm"); "um" and "er" join them for English speech only, by the detected or the chosen language, unless the list is empty — with the commas and pauses around them, keeping a capital at the start of a sentence; a sound joined to a word by a hyphen stays.
- Fillers go first, then the user's replacements. A dictation typed while spoken removes them as replacements in the same `Replacer` for its typed and its final text, so the two agree.
- With a model the orchestrator gives plain dictation an `LlmJob` with the built-in `INSTRUCTION` and the chosen connection; the session then processes like a language-model mode and is not typed while spoken. A missing connection leaves only the fillers removed.
- Files and other modes are not cleaned: a file takes a language model only from a mode that processes (`file_llm_job`).

## Modes by application

`domain/app_rules.rs`, `Settings::app_rules`: the user ties a mode to a program (`AppRule`: the program's id or a typed name, its name, the mode); the app never adds or suggests a rule.

- At the press of the "by application" hotkey (`HotkeyAction::ByApp`, `Settings::app_hotkey`) the controller asks `Services::app_identity` for the program of the focus target (`platform::app_identity`: the bundle identifier and name through `NSRunningApplication` on macOS; the program file's name, such as `Telegram.exe`, through `QueryFullProcessImageNameW` on Windows; `None` for this app) and dictates with the first rule's mode (`mode_for`: the rule's id against the program's id or name, without case and a trailing `.exe`), else with `main_mode_id`. A mode chosen so is reported as `DictationEvent::ModeByApp` and the capsule names it while recording.
- The main hotkey always dictates with the main mode, so plain text stays one press away in a ruled program; mode hotkeys and the selected-text hotkeys are not affected either; a recording stops only with the hotkey that started it, or ends when the settings no longer name that hotkey (`names_hotkey`), so the microphone never stays open.
- Every program dictated into goes to `RecentApps` (in memory only, the latest 12; command `recent_apps`), which the mode editor offers next to a typed name.
- `save_settings` drops the rules of a removed mode, empty ones and a second rule for the same program (`tidy`); the controller also ignores a rule whose mode is gone.

## Context

`domain/context.rs`: a language-model mode may let its model see more than the dictation (`ModeAction::Process::context`, `ContextSources`: the selected text, the clipboard, the program's name; all off by default).

- Reading. The sources are read at the hotkey press, while the focus is where the user was: the program's name comes from `app_identity`, the selected text and the clipboard from `Services::read_context` on another thread. The clipboard source is read before the selection is copied.
  - `platform::selected_text`: Accessibility or UI Automation, also read-only fields, never a password field, no permission prompt. A program that does not expose its selection (Telegram, most web pages) gets it copied with ⌘C or Ctrl+C, and the clipboard is put back: on macOS every item with all its types, on Windows every format but OLE's bookkeeping and those Windows makes again from the kept ones, so there the copy is skipped only while the clipboard holds a handle that cannot be copied (a program's private format). Never in consoles (Ctrl+C would stop the command), and never while a password manager has marked the clipboard private. The copy comes at once, and on Windows the modifiers of a hotkey still held go up around it and back down. A selection copied so passes through the system clipboard: a clipboard history (Windows' Win+V and its sync, macOS' Universal Clipboard, clipboard managers) may keep it, and the clipboard put back as a new copy.
  - `platform::clipboard_text`: `NSPasteboard` or `CF_UNICODETEXT`, text only; nothing from a clipboard a password manager marked private.
- Limits. Each source is trimmed and cut at `CONTEXT_LIMIT` (12 000 characters) with a mark. `PendingContext` travels with the session and is waited for (at most 3 s) on the model's thread.
- Prompt. `engines/llm/prompt.rs` puts it before the source text in a `<context>` block with `<app>`, `<selected_text>` and `<clipboard>`, data under the same rule as the source text, with numbered tags if any text mentions one; without context there is no `<context>` block and the prompt says nothing about one.
- Privacy. The context never goes to the history, the last transcription or a log: the log line `language model context: …` before each call with context shows only which sources went and their lengths (`Context`'s `Debug`). Rewriting the selection, files and "clean text" send no context. The mode editor warns that ticked sources go to the service unless it runs on this computer (`isLocal`).
- Interface. While recording, a paperclip in the capsule shows that the dictation takes context: `DictationEvent::ContextTaken` once a source had text (the program's name at once, the others by `Message::ContextRead`, also when they were read before the microphone opened).

## ChatGPT through the account

See `engines/chatgpt.rs`.

- Sign-in. `connect_chatgpt` signs in in the browser (PKCE, a loopback listener on `127.0.0.1:<port>/auth/callback`, a client registered on the first sign-in and reused, the ID token checked with OpenAI's keys) and needs the granted scope `chatgpt.tokens.use.direct`; `cancel_chatgpt_sign_in` stops it, and a sign-in cancelled or replaced by a newer one after the browser answered saves nothing (`ChatGptSignIn::finish`). Tokens that are not kept — a cancelled sign-in, a failure after the code exchange (`chatgpt::sign_in`), the model list or the saving failing (`discard_sign_in`) — are revoked in the background (`chatgpt::end_session`), and after a first sign-in the registration loses its ID token. The registration (`chatgpt-registration` in the secret store) sends `id_token_hint` and `login_hint` only while signed in, and `prompt=consent` after plan usage was declined. A registration OpenAI no longer knows (ahem removed in ChatGPT's settings: another client in the answer, or `invalid_client`) is forgotten, and the user signs in again (`ClientForgotten`).
- The connection (`ProviderKind::ChatGptAccount`, named by the account's email) keeps its tokens as one record in the secret store; `chatgpt::access_token` renews them before a request on the worker thread.
- Requests. `llm::Provider::ChatGptPlan` streams `POST /v1/responses` with `store: false` and no output limit; `PlanLimit` inserts the transcript (`FailureKind::PlanLimit`) and the dictation card offers "Manage usage" (`open_chatgpt_usage`). The mode editor shows "Using ChatGPT plan" for its models.
- Disconnecting (`remove_connection`) saves the settings, then `chatgpt::sign_out` forgets the tokens under the renewal lock, so a renewal running then ends first and none is saved after, and keeps the registration without the ID token; `revoke_retrying` revokes the latest refresh token when OpenAI publishes a revocation endpoint, twice more after no answer, a 5xx or a 429, and the row says when OpenAI did not confirm it or the tokens could not be read (`sign_out_unconfirmed`), showing "Disconnecting…" meanwhile.

## Replacements

`domain/replacements.rs`: the user's pairs "phrase as the engine writes it → text to put instead" (`Settings::replacements`), so corrections and snippets work with every engine, also the ones that ignore the dictionary.

- One entry may list variants separated by commas or new lines. A phrase matches in any case, as whole words, with any spaces between its words; the longest phrase wins and inserted text is not replaced again; an empty replacement removes the phrase with the commas and pauses written around it and leaves a capital at the start of a sentence, as `remove_fillers` does (`render`); a sound joined to a word by a hyphen stays.
- The orchestrator applies them to a dictation's transcript before the mode's language model, so the history and the last transcription keep the replaced text. While a streaming model types, `Replacer::settled` holds back the end of the text where a phrase may still be completing, and the spaces, commas and dots at its end, so nothing typed has to change (tested over thousands of random phrases). A dictation typed while spoken is cleaned of fillers the same way at its end; one of which nothing was typed, by `remove_fillers`.
- In a file, `files::replace_words` joins the words a phrase spans into one word with their times, reading the words before it for where a sentence starts (`render_after`) and giving a removed word's capital to the next; `transcribe_file` takes `replacements` (on by default in the interface, never for a `.txt`).
- Commands `export_replacements` and `import_replacements` write and read `{"replacements": [{"from", "to"}]}`.

## Motion

Interface only: the tokens `--ease`, `--ease-out`, `--d1`–`--d3` at the top of `App.css` (repeated in `indicator.css`) time every animation; mostly transform, opacity and clip-path move (sizes where the size is the point, e.g. the navigation thumb, the capsule's parts, the level bars, the progress bar, a new row of the history), and the system's reduced motion stops them. The capsule keeps all its parts and folds the unused ones, so its width flows between states; it fades just before the backend moves it away (the lingers of `indicator.rs`). `useThumb` in `ui.tsx` slides the highlight of the sections and of the quick panel's modes; `useFresh` marks new rows of the history and the quick panel, not the ones a list read as it is shown brings.

## Updates

`updates.rs` and the `tauri-plugin-updater` plugin. Twenty seconds after the start and then every twelve hours the app asks GitHub for the manifest `latest.json` (the newest release that is not a pre-release; with "Beta versions" on, the release tagged `beta`, whose manifest names the newest version of either kind). Nothing is checked in a development build. A newer version comes to the interface as `CoreEvent::Update` (`UpdateEvent`): `update.ts` turns it into `UpdateState`, and `components/UpdateCard.tsx` shows it in the menu and the quick panel.

- Without "Update automatically" the card says that a version exists; "Update now" (`install_update`) downloads it, shows the progress, installs it and restarts the app. With it on, the package is downloaded in the background at the check, and the card appears when one press installs it (`ready`).
- The package is signed with minisign: the public key is `plugins.updater.pubkey` in `tauri.conf.json`, and the plugin installs only a package that it accepts. The endpoints are in code (`STABLE_MANIFEST`, `BETA_MANIFEST`), HTTPS only, and the plugin's own commands are granted to no window. The plugin uses the system's TLS (`native-tls`), not the bundled certificates.
- Before the program is replaced the app lets go of what it holds (`shut_down` in `lib.rs`: the engine processes, a meeting being recorded, which is kept), and it restarts after the installation (on Windows the installer does it). The version that ran last and the notes of the one being installed are kept in `update.json` of the data folder; the first start after an update tells "Updated to …" with those notes and a link to the release page.
- A release is built by `.github/workflows/release.yml` when a tag `vX.Y.Z` is pushed, on macOS (Apple silicon) and Windows runners: the engines are fetched or built (`tools/fetch-*`, `tools/build-engine`), `tools/stage-engines` (`.sh`, `.ps1`) gathers `whisper-server` and `llama-server` with their libraries into `src-tauri/engines/`, and `tauri build --config src-tauri/tauri.release.conf.json` carries them in the installer (`engines/` of the app's resources, found by `engine_dir` of `whisper_server.rs` and `llama_server.rs`) and makes the update packages, signed with the private key in the secret `TAURI_SIGNING_PRIVATE_KEY`. `tools/update-manifest.mjs` writes `latest.json` from the packages' `.sig` files (plugin's static JSON: `version`, `notes`, `pub_date`, and in `platforms` — `darwin-aarch64`, `windows-x86_64` — the `url` of the package and its `signature`); the workflow makes a draft release with the installers and `latest.json`, to be checked and published by hand. The installers are published under fixed names, the same in every release: `ahem-macos-arm64.dmg` and `ahem-windows-x64-setup.exe` (so `releases/latest/download/<name>` always gives the newest one); the Windows update package is that same `ahem-windows-x64-setup.exe` (the updater checks the signature against the file's bytes, not its name), and the macOS one keeps the name Tauri gives it. An extra `"urgent": true` in the manifest marks a fix of a serious defect. The same steps by hand: run the `tools/` scripts, `tools/stage-engines`, then `tauri build --config …` with the key in the environment. The beta channel reads the release tagged `beta`; none is published yet.
- The settings fields `auto_update` and `beta_updates` are off by default; their two switches in Settings → General follow `UPDATES_READY` in `update.ts`, which a test keeps in step with the registration of `install_update`.

## Development files

Outside the source, in `runtimes/` (ignored by git):

- `runtimes/whisper-<version>-<os>-<arch>/` — the whisper.cpp engine from `tools/build-engine.ps1` (Windows) or `tools/build-engine.sh` (macOS).
- `runtimes/llama-<build>-<os>-<arch>/` — the official llama.cpp build from `tools/fetch-llama-cpp.ps1` / `.sh`.
- `runtimes/sherpa-onnx/` — the official prebuilt sherpa-onnx libraries from `tools/fetch-sherpa-onnx.ps1` / `.sh`, read by the build through `SHERPA_ONNX_ARCHIVE_DIR` (`.cargo/config.toml`).
- `runtimes/build/` — the scripts' downloads and build trees.
- `runtimes/models/` — models for ignored tests; `runtimes/test-audio/` — synthesized test speech.

The app finds `whisper-server` and `llama-server` in these folders of the source tree (`dev_engine_dir`, a path fixed at build time); the installer does not include the engines. The engine scripts cover Windows (`.ps1`) and macOS (`.sh`); there are none for Linux.
